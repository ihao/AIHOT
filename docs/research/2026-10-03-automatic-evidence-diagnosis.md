# 自动核验接受率 6% 与“缺少证据”诊断

本次为生产只读诊断，未修改规则、来源配置、审核结果或公开授权，也未触发付费模型请求。

## 结论

接受率低的主要原因是：**一手证据要求覆盖范围过宽，而系统实际取证能力较窄，两者叠加拦住大量媒体、研究和治理讨论内容。** 同时存在真实的文案缺证、引文不匹配和格式问题，不能把全部拒绝结果当作误判，也不能把低接受率当作原文真实性统计。

北京时间 **2026-10-03 22:48:18** 的 PostgreSQL 只读一致性快照与用户截图吻合：接受 17、拒绝 252、等待 0、“缺少证据”219；另有 6 条核验失效。API、worker、web 使用同一镜像，实际运行的审核代码、提示词与本地对应文件的 SHA-256 一致。

详细决定于 22:50:59 再次只读采样，按首个快照时间截取创建记录，得到同样的 275 条记录及状态计数。原始终止决定保留在数据库的 `decisions` 字段中。本报告的数量均按这一与截图一致的记录集合计算。

## 2. “缺少证据”的实际标准

### 普通报道的证据

标题、摘要和非空推荐理由中的全部主要主张，都必须能从**本次已抓取的正文材料**找到支持；不能使用模型常识、未抓取链接或模型自行添加的来源。

每条主张须附材料 ID 和连续原文引文。代码仅规范化空白，随后检查引文是否为对应材料正文的连续子串。改变标点、弯引号与直引号、拼接句子、改写或翻译引文，都可能触发 `quote_invalid`。即使审核模型说 supported，这项程序检查失败仍会拒绝。

所有整体检查也要通过，包括主张完整性、中文忠实程度、主体、数字、单位、时间、链、阶段、归属、推测与事实区别、非营销。未表达的维度不应强制补证。

### 什么时候要求一手证据

对于 `first_party=false` 的来源，符合下列任一条件就会把**整篇文案**设置为需要一手证据：

1. 分类是安全、政策/监管等指定分类；
2. 内容类型命中 security、policy、governance、attack、loss 等模式；
3. **原文标题或全部正文**出现指定关键词，例如 SEC、regulatory、proposal、vote、loss、治理、提案、投票、监管、执行。

第三项不是对摘要主张的语义判断。“首席执行官”里的“执行”、市场价格损失、招聘岗位中的监管法务、旧事件背景里的治理提案，均可能触发整篇要求。

此外，审核模型只要返回任意非空 `riskFlags`，程序同样要求**每个主张**有一手证据，而不只检查风险主张本身。输入材料的一手属性来自来源配置/取证程序，模型不能自行认定。

因此，当前代码比“攻击确认、损失金额、监管结果、治理执行等关键事实需一手证据”更严格：**一处命中，会升级整篇的全部主张。**

代码依据：`packages/backend/src/editorial/automatic-verification.ts:185-214`；`packages/backend/src/editorial/automatic-policy.ts:76-112`；提示词 `industry/prompts/verify-summary.md:5-13`。

### 补证能做什么

系统不是开放式搜索取证。它只从已存原文 HTML 的 `<a href>` 中选取前 **2 个**符合固定域名白名单的 HTTPS 链接。

域名必须精确匹配白名单或对应的 `www`，不能任意继承子域。每一跳重定向也要符合规则；只接受 HTTP 200 的 HTML/XHTML 正文，提取正文至少 200 字符。没有“其他媒体交叉证实”的替代通道；PDF、API JSON、GitHub、X、治理论坛等也没有通用取证通道。

这些限制中的身份校验本身有必要，但当前来源覆盖面与取证覆盖面不匹配。名单中有 ethereum.org、sec.gov、aave.com 等，却没有本次样本里的 fsc.go.kr、docs.dogeos.com、governance.aave.com 等。加入一个域名也不能直接证明事实，仍需抓到相关正文并逐条核验。

代码依据：`industry/evidence.ts`；`packages/backend/src/editorial/automatic-verification.ts:195-242`；`packages/backend/src/content/extract.ts:23-36`。

## 3. 252 条拒绝实际卡在哪里

下表统计**初次检查**，各项可能重叠，不能相加：

|问题|拒绝记录数|含义|
|---|---:|---|
|至少一个主张缺一手证据|216|主要瓶颈|
|全部初次拒绝理由仅为缺一手证据|74|其余初次门禁已通过，但不代表这些事实已被独立证实|
|至少一个连续原文引文不匹配|117|模型引用与程序核对不一致，可能与一手证据问题同时发生|
|至少一个主体、数字、归属等整体检查失败|52|仍有实质性文案问题或证据不足|
|中文文案/分类不完整|21|属于文案结构问题，不应笼统显示成缺证|
|审核模型初次明确判断存在矛盾|8|是初次模型判断数量，不是人工确认的虚假新闻数量|

176 条被拒绝记录的初次模型总 verdict 是 supported，但程序门禁仍拒绝。其中仅有 74 条的初次程序拒绝理由全部是一手证据不足；其余还有引文或其他问题。**模型 supported 只表示其认为文案有输入材料支持，不证明材料报道的现实事实真实。**

最终 **194 条**以 `no_new_primary_evidence` 结束，占拒绝记录 **77.0%**，也占“缺少证据”219 条的 **88.6%**。这 194 条的取证链接数组均为空，重新按当前运行函数检查已存原文，也均没有可接受的补证链接。它们不是“尝试抓取官方材料后全部失败”，而是原文里没有系统允许取的链接。194 条中有 148 条的初次模型 verdict 为 supported。

37 条记录取得了额外材料，其中仅 1 条接受、36 条拒绝。这说明仅增加链接数量还不够：材料的相关性、引文有效性、每条主张的证据要求和文案质量都影响结果。

还有一个流程问题：needs_evidence 默认走补证；没有补到新材料就直接结束。只有明确 contradicted 才优先走改写。因此，一些能够通过删减无支撑扩展句或推荐理由改善的稿件，也可能没有得到这次改写机会。

代码依据：`packages/backend/src/editorial/automatic-verification.ts:405-440,535-542`。

## 5. 为什么“缺少证据”标签难以理解

后台 219 的计算条件是以下任一项成立：最终理由包含 `verification_needs_evidence`、`no_new_primary_evidence`、`verification_missing_or_invalid`，或模型最后 verdict 是 needs_evidence。

因此它同时可能包含：缺一手正文、普通主张缺支持、整体检查失败、结构化核验结果无效。“没有新的一手材料”还会覆盖掉最终理由中的较早具体问题；具体问题仍保存在 `decisions`。

反过来，部分最终理由为 `claim_*_primary_evidence_missing` 或 `quote_invalid`、而模型 verdict 仍为 supported 的记录，可能不计入 219。所以这也不是全部证据问题的完整计数。

## 6. 建议的修正方向

1. **按具体主张确定证据等级。** 一般媒体报道可保留来源归属；研究与观点明确作者、方法和估计口径；攻击确认、损失、监管最终结果、链上执行等关键结论继续要求相关一手证据。不能仅因原文出现“执行/监管/proposal”就把所有主张升级。
2. **区分提出、宣布、批准与执行。** 治理论坛中的“经认证作者提出某方案”可以是该作者声明的一手材料；“已执行”仍需执行记录。机构研报可支持“该机构估计”，不自动支持独立客观确认。
3. **补齐经过身份验证的取证能力。** 按发布主体、官方文档、治理作者/提案、指定仓库等扩展来源识别，保留相关正文核验；不应给 GitHub、X 或整个论坛开放无条件一手权限。
4. **改进可修复文案。** 对无支撑的扩展句、推荐理由与引用格式进行受限修正后重新核验。不能用改写把真正缺失的关键证据变成已确认。
5. **后台显示具体阻塞。** 分开显示无原文链接、链接不在允许范围、抓取失败、主张缺证、引文不匹配、文案格式失败；同时展示当前文章结果与原始核验轮次指标。

这些是基于已确认根因的建议，**本次没有实施或降低门槛**。修改标准前应使用真实 Web3 样本校准，不能以提高接受率为唯一目标，也不能把 74 条初次仅缺一手证据的记录批量直接放行。
