# 生产“全部 Web3 动态”低价值内容收录根因与解决方案

审计日期：2026-10-14。生产统计快照：北京时间 18:09:38；公开 HTTP 核验约 18:11。范围为生产数据库、实际运行容器、当前源码及升级前后差异。本次仅诊断和提出方案，没有修改业务规则、生产数据或调用付费模型。

## 结论

问题确实存在，且有两个独立原因：

1. **全部动态没有最低价值分门槛。** 评分只决定是否精选以及使用哪种写作方式；0 分内容只要最终相关性为 `pass`、标题摘要完整，就能进入公开池。这是原有机制的产品规则缺口，10 月 10 日之前已经存在。
2. **10 月 10 日升级引入相关性回归。** 预筛 `UNKNOWN` 在写出标题摘要后被 `normalizeAnalysis()` 改成 `pass`，违背本站提示词“UNKNOWN 等待补材料”的要求。今天的 0 分书目就是通过此路径收录。

另外发现论坛全站 RSS 混入书目和分类说明、预筛将平台上的普通概率报价当成平台实质进展，以及一篇材料只提取到媒体声明。这些是噪声入口和材料质量问题；评分已给出低分，最终公开准入却没有利用这些信号。

## 根因链路

### 1. 原有规则没有“收录最低分”

`packages/backend/src/publication/rules.ts:28–36` 的 `isPoolEligible()` 只检查：

- 来源属于 editorial；
- 最终相关性为 pass；
- 有标题，以及摘要或可展示的原帖。

该函数没有分数参数。`publication/publish.ts:286` 据此写入 `publications.eligible`，`publication/scope.ts:24` 的统一列表读取再使用它。

`industry/selection.ts` 的 60 / 65 / 76 是精选门槛；`understandFloor=50` 只决定用内容理解还是较便宜的标题摘要写作。它们均不是全部动态的最低收录分。

`editorial/analyze.ts:420–428` 对低分仍调用 `runSummarize()`，`normalizeAnalysis()` 将文案完整作为相关性通过的条件。因此链路是：

**预筛放行 → 两次评分很低 → 仍生成中文标题摘要 → 全部动态准入不读分数 → 公开。**

### 2. UNKNOWN 被文案完整性覆盖

升级前的自动模式含有明确的保护：

```ts
(mode === "automatic" && label !== "PASS") ? "unknown" : ...
```

合并提交 `a3f5399` 删除了这项判断。当前 `editorial/analyze.ts:442` 除了 BLOCK 和文案不完整外，都归为 pass。于是 UNKNOWN 也能变成 pass。

站点预筛提示词仍明确：不能凭来源或名称补全；UNKNOWN 等待补材料。代码与本站业务要求失配。当前公开集合中，原始 UNKNOWN 共 7 篇，其中 4 篇低于 10 分，3 篇为 15 / 15 / 18 分，全部不是精选；这 7 篇分析均发生在升级后。

在生产 API 容器中只调用实际的两个纯判断函数，使用合成内存输入复现：UNKNOWN、评分 `[0,0]`、标题摘要完整时，返回 `relevance=pass, score=0, selected=false, eligible=true`；预筛 PASS、评分 `[0,0]` 同样 eligible=true。该验证无模型调用、无数据库写入，见 [运行复现](2026-10-14-low-value-content-audit/runtime-reproduction.json)。

### 3. 噪声入口和材料校验仍需补齐

- Flashbots、Uniswap、Rocket Pool 使用论坛 `/latest.rss`；不仅采集协议进展，也收书目、分类描述和申请讨论入口。不能将整个论坛来源一律视为新闻。
- CNBC 两篇案例仅给出 Kalshi 对外部事件的概率报价。现有提示词提到“有数据和方法的研究”，但模型把普通报价及结算依据当成平台机制新闻；应增加明确反例，区分平台规则改变、研究方法与单纯报价。
- Evernorth 案例的正文状态虽为 ok，但实际只是编辑政策声明。正文提取的字符长度合格不等于新闻正文有效，需验证主体、正文结构及样板声明。本例不支持扩大为“所有 Cointelegraph 内容都提取失败”。
- `[0,1]` 展示为 0 是 `floor((0+1)/2)` 的既有规则。另两篇是确实 `[0,0]`，不存在以“评分失败默认填零”解释全部问题的证据。

## 建议方案

### 第一阶段：修复确定的问题

1. **新增全部动态准入下限。** 以“明确拒收个位数和 0 分”为第一阶段范围，最低有效分设为 10；没有人工评分更正时，等价于要求两次完整评分之和至少为 20。有人工评分更正时使用更正后的有效分，不能退回原始高分绕过拒收。配置放在本站 `industry/selection.ts`，与精选门槛分开。未评分、评分不完整或拒绝评分保持内部待确认，不能以默认零值或来源级别豁免进入公开池。人工更正继续保留原始评分与审计。
2. **UNKNOWN 不得自动公开。** 修复最终相关性判断，只有原始预筛 PASS 且材料、文案满足要求才能自动准入。UNKNOWN 保留在内部，确有可补材料时按现有修订处理；不自动反复购买相同输入的评分和写作。BLOCK 继续拦截。
3. **将判断放在统一发布层。** 所有列表、搜索、主题、RSS、v1、Agent/MCP 使用同一准入结果和拒收原因。不得仅给 `/all` 加前端过滤。特别注意现有 `hasItemPage()` 不检查 eligible：只改 eligible=false 仍会留下公开详情和 Markdown，必须同步检查质量拒收状态或撤回其公开版本。
4. **减少不必要的后续处理。** UNKNOWN 不满足准入时先等待；已有完整低分结论后不继续生成公开用摘要或排入公开事件归组。原始材料、分析、回执和已发生费用全部保留。结构化目前与评分并发，不能声称评分后拦截能追回已经开始的结构化费用。

这里的 10 分是针对用户已明确指出的拒收范围提出的第一阶段边界，尚未实施，不代表 10 分以上都值得收录。

### 第二阶段：有针对性地处理来源和材料

- 对论坛先统计噪声分类与有效提案，验证 category ID 后收窄入口或增加有证据支持的条目过滤；保留实质治理、协议及安全内容，不一刀切停用整个来源。
- 增加书目、论坛分类描述、活动指南、空的申请讨论入口及纯概率报价反例；同时加入真实的治理执行、重要研究和平台结算规则变化作为正例，避免用标题关键词误杀。
- 针对已证实的正文样板误提取增加有效性判断；正文无效时待补材料，不能从标题扩写成已核实新闻。使用保留的原始材料进行隔离回放验证。

### 第三阶段：校准更高的价值门槛

分数 10–29 的公开记录还有 917 篇，最低分 10 只能解决明确的个位数问题。建议抽取 100–200 条分层样本，覆盖营销、行情、论坛、治理、研究、监管与安全，并重点检查 10–39 分的边界案例。先标“应收录 / 不应收录”，再评估 20 / 30 等候选门槛，保留独立留出集。

| 拟议最低分 | 仅按分数移出 | 加上 UNKNOWN 移出 | 当前精选受影响 |
|---|---:|---:|---:|
| 10 | 17 | 20 | 0 |
| 20 | 503 | 503 | 0 |
| 30 | 934 | 934 | 0 |
| 40 | 1,359 | 1,359 | 0 |
| 50 | 1,893 | 1,893 | 0 |

30 分会影响当前公开集合约 32.2%，因此不能仅凭分布直接批量撤回。根据 `AGENTS.md` 和 `docs/selection.md`，更高门槛应使用用户标注样本校准；本次只给出影响预估，没有擅自修改数字或宣称这些记录全部无价值。

## 历史处理和上线验收

历史处理应只复用保存的评分及预筛结论，不删除原始文章，不批量重跑模型。

1. 实施前保存数据库、公开/精选 ID 集合、受影响 ID 与旧发布状态；列出最终拒收清单和原因，考虑保留人工更正。
2. 先部署新的统一准入，再分批从已有结果重建公开投影。重建时必须读取 `output.prefilter.label`，不能继续信任旧 `analyses.relevance=pass`；否则 UNKNOWN 历史稿仍会放行。
3. 第一阶段预计移出 20 篇：17 篇低于 10 分，加上另外 3 篇高于此线的 UNKNOWN。数据库和费用记录留存，内部仍可诊断，公开详情/Markdown及事件页面不能绕过拒收。
4. 更新搜索、主题、事件引用、热点和相关缓存；检查既有报告是否引用受影响内容，需要时按既有更正流程处理，不自动重写所有旧刊。
5. 验收至少包括 0、9、10 分边界，UNKNOWN 即使有完整摘要/较高分仍不自动公开，评分缺失、BLOCK、有效治理/安全正例、人工更正、历史重建及原帖路径。网站、搜索、主题、RSS、API、Agent/MCP、详情和 Markdown 均核对拒收状态。
6. 以实际公开集合比对验收：第一阶段受影响 ID 应全部退出公开；当前 285 篇精选的 ID 集合应保持一致，正常新增单独核算。观察后续真实采集周期，确认不会再产生个位数公开稿和 UNKNOWN→pass 泄漏。

本次证明了生产问题、实际判断路径、回执真实性、升级回归和静态影响范围；未实施修复，未进行修复后的回归或生产发布验收。后续费用节省仍需实际请求及供应商账单验证。
