上游 [b3998dc](https://github.com/KKKKhazix/AIHOT/commit/b3998dc6fc138eb9659f33f55eb38c1c716f0d57) 明确将 Fastify、undici 与 Node 的升级列为安全更新；[85a1632](https://github.com/KKKKhazix/AIHOT/commit/85a1632878bbbd4e4978a0e73d9f71c1a20a7e88) 说明 zod 修复超大受约束集合校验可能耗尽内存的问题。这构成近期升级依据，但本次没有独立做漏洞利用或攻击暴露面验证。MCP 和 Vite 版本变化不自动等同于安全漏洞。

边界：b3998dc 引用的 sanitize-html GHSA 明确涉及 `2.18.0`；不能把生产的 `2.17.7` 直接判为受该特定漏洞影响。升级目标应采用修复后的 `2.18.1`，不要停在中间版本。

### 采集、正文与日期：与本站费用保护直接相关

- 登录/注册页、跳转和错误页的拦截，减少错误页面被当作文章正文。
- 相对时间、中文短时间单位、来源时区及原始时间精度修复，与本站 48 小时自动处理门禁密切相关。
- 列表尾部动态计数不再构成材料修订，减少无意义版本变化和后续处理机会，实际费用收益待验证。
- X 分片账号水位、Jina 列表请求身份、TLS 密钥交换失败的限定重试及翻译恢复，可按生产启用的来源类型吸收；仅在使用相关渠道时有直接收益。

上游也变更了对象存储备份凭据读取与保留前缀，完整同步前需核对本站备份注入和保留策略；本次未读取凭据或测试对象存储备份。

## 3. Spec：必须保留的本站差异

以下四类以长期决策 D01–D06 为依据。上游行为本身服务于其产品目标，不能因此直接判为上游缺陷。

### S1 发布与精选门槛（D02）

本站要求预筛 PASS 才继续自动评分/写作；统一公开门禁保留 `publicFloor=10`，未评分及低分不公开，低分不购买公开文案。上游 `editorial/analyze.ts:485,514` 只拦 BLOCK，UNKNOWN 可继续处理并因生成文案成为 pass，不能覆盖本站规则。

上游新增 `browseFloor=40` 是浏览列表、全部模式 API/RSS 的展示过滤，未评分仍允许展示，搜索仍覆盖全部（`industry/selection.ts:31-34`、`publication/scope.ts:32-33`）。它与本站的全出口准入不是同一个门槛，不能把 10 机械改成 40，或用该过滤替代既有门禁。

上游新增信源类别门槛下限，示例类别与 AI 行业相关。9BTC 七类 key、Web3 提示词、主题、来源授权和阈值必须保留；是否采用信源类别需另做样本校准。预测市场筛选、BTC/USD 首次入库不可变绑定、品牌与 EU 部署继续保留。

### S2 未知计费、fallback 与金额保护（D06）

上游 `operations/recover.ts:45-55` 允许 unknown 回执在超时后自动放行一次；本站同文件明确排除模型、向量与评测，继续保留金额预留。本站规则必须保留。

上游 `providers/llm.ts:148-160` 的跨供应商 fallback 可在主请求 unknown 时发起第二个付费请求。默认预设没有声明 `fallbackFor`，因此不能说升级后默认一定产生备用模型费用；但不能在未完成本站预算和未知计费适配前启用。

生产金额硬限额目前关闭，尤其不能把“所有调用经过回执”当成金额上限必然生效的证明。原有金额预留/结算、缓存 token 计价、价格证据、按共享凭据暂停和评测独立额度均需保留。

### S3 报告历史补期（D04）

上游 `reports/compose.ts:318-319` 从最早已有期遍历旧缺期。本站 `automaticKinds` 与 `catchUpHistory=false` 只生成最新到期一期，应继续保留，不能因框架同步启动批量历史补期。空白周/月跳过与停止时不报失败等通用修复可以吸收。

### S4 新增付费能力（D06）

- 上游 `events/cards.ts:59-73` 新增 `group_card` / `group_card_review` 模型比较，提升精选卡片去重能力，同时增加新的模型请求。需要接入本站预算及在历史样本上测量请求量、重复减少和误折叠。
- 上游 `operations/feedback.ts:227-252` 增加 `judge_feedback` 反馈噪声判别；仅飞书内部转发可用时触发，并非所有部署默认调用。需核对本站实际启用条件及费用，不能当成零成本界面更新。
- Agent 告警中台、群机器人通知、内网订阅放行等新增配置依具体运营需求决定，本次不启用。

Spec 汇总：4 类需要保留/适配的业务差异。最重要的是发布门禁与未知计费边界；即使文本自动合并成功，也需要回归证明语义未变化。

## 4. 同步建议与完成标准

**第一阶段：近期完成小范围安全与可靠性更新。** 针对安全提交更新 Node/依赖和锁文件，选择不改变内容规则、付费策略的明确修复，完成回归后固定镜像发布。可以通过小范围提交暂时降低风险；长期同步仍采用正常双父增量 merge，保留上游祖先。此处是建议，尚未执行升级。

**第二阶段：以 `cd424b0` 为固定目标完成完整整合。** 逐项处理 30 个冲突文件，特别审查自动合并的公开读取、归组、报告和模块接点。保留 D01–D06，在生产快照恢复出的隔离库中演练迁移，确认原始材料、分析、归档、回执、金额账本、来源设置、报告和 BTC 绑定保全，重复迁移为空操作。

验收需包含类型检查、后端/网页回归、构建和真实浏览器检查；对采集日期/正文用真实公开来源样本比较前后差异，模型测试使用本地假服务及外网阻断。逐项核对列表/详情/搜索/RSS/API/MCP/事件出口门禁、未知计费不自动重发、旧分析不因提示词改变重新购买、报告不补历史、默认不增加模型。需要新增付费能力时，先测量调用量并明确采用决定。

发布前使用可恢复备份，验证 EU 停止宽限与新版排空窗口一致；发布后核对任务恢复、费用预留、公开/精选集合及公网出口。不要将本次只读审查或 merge-tree 模拟当成合并后的测试通过证明。
