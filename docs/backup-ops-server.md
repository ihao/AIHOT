# 9BTC 异地备份实施记录

状态：**方案与脚本已准备，尚未启用**。2026-09-30，站长决定不使用第三方对象存储，改用 OPS 管理的另一台服务器。

## 接收端选择

选择 OPS 中的 `naban`（`110.42.197.165`），不使用旧 `9btc` 服务器。只读检查时，naban 的根分区约 69 GB，剩余约 47 GB；EU 可连通其 SSH 端口，双方已有 `rsync`。其他候选：`tencent` 仅余约 17 GB；`jenkins-new` 虽有大数据盘，但系统是已停止维护的 CentOS 7，且承载 Jenkins、JumpServer 等业务。容量和系统状况均须在启用时再核对。

## 拟实施的隔离方式

1. naban 新建无密码、无 sudo 的 `ninebtc_backup` 账号，主目录 `/srv/ninebtc-backup` 权限 `0700`，下面只有 `daily/`、`weekly/`、`monthly/`。不修改现有 SSH 服务配置或业务目录。
2. EU 现场生成只供此任务使用的 SSH 密钥。naban 授权公钥限定来源为 EU IP，并使用 OpenSSH 的 `restrict` 选项；EU 固定核对过的 naban 主机公钥。私钥只留在 EU 的 root 专用目录，不入 Git 或聊天记录。
3. EU 安装 [备份脚本](../deploy/offsite-backup.sh)和 [systemd 定时器](../deploy/ninebtc-backup.timer)，每天北京时间 04:10 导出 PostgreSQL 自定义格式备份并打包站点上传文件。先检查归档可读，再经 SSH/rsync 发送并核对双方 SHA-256。站内反馈截图不进入这份上传文件包；数据库中的反馈记录会进入数据库备份。
4. naban 留存每日约 7 天、每周约 28 天、每月约 92 天；只删除新建的 9BTC 备份目录中符合命名规则的过期文件。EU 本地短留约 3 天。站点服务和 naban 既有备份不受影响。
5. 从 naban 把实际备份取回 EU，恢复到**新建的独立测试数据库**，核对迁移和基础表数量。测试库不覆盖业务库；完成后记录结果。定时器首次成功后再将异地备份视为已生效。

## 当前未完成

在 naban 创建新账号的第一次执行被自动审批审查拒绝，因此**naban 尚无接收账号，EU 定时器尚未安装，异地自动备份尚未生效**。审查认为远程账号创建和权限变更需要更明确的授权，且原命令额外复制了 `/etc/shadow` 等认证文件。后续实施方案已删去复制认证文件这一步；仅在取得明确批准后创建专用账号及目录。现有同机数据库导出和恢复演练不能替代异地备份。

启用异地备份后，须同步更新[隐私说明](../industry/pages/privacy.md)，说明 9BTC 反馈数据的备份副本存放在 OPS 管理的 naban 服务器。若需要停止任务，先停用 EU 的定时器并保留已产生的备份和接收账号，待核对后另行处理，不删除任何既有业务数据。
